# Как пополнять tiny1C

## Правило рождается из ошибки, а не из желания написать правило

В набор попадает то, что кто-то проверил на живой системе. Поле `источник`
обязательно и начинается одним из видов:

| Вид | Когда |
|---|---|
| `ошибка:` | правило выведено из реально пойманной ошибки — проект и дата |
| `измерение:` | посчитано по исходникам или прогонам: «в 421 форме встречается…» |
| `эксперимент:` | проверено намеренным опытом на базе |
| `образец:` | собрано по работающему образцу, с указанием какого |
| `решение:` | проектное решение, которое живёт годами и о котором жалеют |
| `документация:` | вывод из публичной документации, со ссылкой |

Правило без источника отклоняется механически — `scripts/hygiene.py` не даст
такому файлу пройти.

## Правило называет свою проверку

Поле `check` — список записей «вид:описание»: что упадёт, если правило
нарушить. Если ничего не упадёт, пишется `manual:` и текст, как это ловит
человек. Пустой `check` запрещён: правило, о котором неизвестно, чем оно
ловится, невозможно ни соблюсти, ни опровергнуть.

Хороший признак зрелости набора — доля правил, у которых `check` не `manual`.
Она видна в манифесте (`ловятся_только_человеком`) и должна расти.

## Чистая комната

Набор пишется из собственного опыта и измерений, а не пересказом чужих
корпусов правил. Практическое правило: **писать при закрытом чужом файле**.
Факты (имена свойств, значения, поведение платформы) свободны; чужие
формулировки, таблицы и сама подборка тем — нет.

Если факт взят из чужого текста, а не из своего измерения, — источник
`документация:` со ссылкой, и формулировка своя.

## Направления

Новое направление — каталог в `tracks/` с паспортом `track.md`. Правила
конфигурации живут в её направлении, а не в `core`: в `core` попадает только
то, что верно независимо от конфигурации.

Направление можно завести пустым: паспорт со статусом `открыто`, глоссарий и
карта объектов полезны сами по себе, ещё до первых правил.

## Правила из портала TinyCIO

Часть правил приходит из «Базы знаний ИИ» портала TinyCIO: находку из работы
с проектом сотрудник доводит до правила по шаблону, и портал открывает PR из
ветки `intake/<номер>` — только файлы правил, без манифеста и README. Workflow
`intake.yml` пересобирает `manifest.json` и счётчики README
(`scripts/readme-counts.py`), гоняет все проверки на итоговом дереве,
коммитит пересборку в ветку и ставит проверку `intake`. Зелёный `intake` —
бот портала сливает PR сам (squash). В PR нет ни имён заказчиков, ни номеров
заявок: чистая комната проверяется ещё в портале, `hygiene.py` — второй рубеж.

Таблицу направлений в `README.md` сверяет с манифестом `scripts/hygiene.py`:
счётчики правил и терминов ставятся руками и расходятся молча, поэтому новое
направление и каждое новое правило требуют правки таблицы — иначе push падает.

## Что нельзя выкладывать

Тексты модулей, макеты и метаданные типовых конфигураций принадлежат их
правообладателям. В набор идут имена объектов, термины и приёмы — не
содержимое конфигураций.

Механическая проверка перед публикацией:

```bash
scripts/hygiene.py
```

Она ищет имена заказчиков, логины и пароли, токены, пути машины разработчика,
следы чужих корпусов и бинарники. Исключения — в `scripts/hygiene-allow.txt`,
каждое с объяснением.

## Заготовка

```bash
scripts/new-rule.py <направление> <id> ["заголовок"]
```

Скрипт кладёт файл из `tracks/_TEMPLATE.md` в нужное направление, проверяет,
что идентификатор свободен во всём наборе, и напоминает про обязательные поля.
Формат id — `тема-001`.

## Конверт правила или рецепта

Если правило или рецепт написано там, где нет доступа к этому репозиторию (другая сессия,
другой проект, чужая машина), оно передаётся одним куском:

```
Файл: tracks/core/rules/forms-011.md
---
id: forms-011
...весь фронтматтер и текст...
```

У рецепта путь другой: `Файл: tracks/core/guides/how-XXX.md` (id `how-XXX`,
настоящий номер присваивает приёмщик).

Получатель сохраняет файл по указанному пути и запускает `scripts/manifest.py`
и `scripts/hygiene.py`. Ничего больше вставлять не нужно: манифест соберётся
сам, а обе проверки скажут, чего в правиле не хватает.

В плагине Claude Code конверт собирает команда `/1c:propose-rule`: она находит в
сессии кандидатов (ошибка платформы, которую разбирали долго; правило из
`checklist` не сработало; поведение не по ожиданию), по каждому спрашивает
человека, собирает файл по `tracks/_TEMPLATE.md` с id вида `тема-XXX` (настоящий
номер присваивает приёмщик) и перед выдачей прогоняет `scripts/hygiene.py --файл
<путь>`. Этот режим проверяет один файл вне дерева: фронтматтер, словари
(категория, серьёзность, платформы, источник, check), образцы приватного, почту,
ИНН и пути; рецепт от правила он отличает сам (есть `задача` или id `how-…`).
Режим без аргументов не изменился.

Так же передаётся правка существующего правила — целым файлом, а не куском:
файл маленький, а склейка кусков порождает расхождение с манифестом.

## Инструменты

Исполняемый инструмент — карточка `tools/<группа>/<имя>.md` (заготовка —
`tools/_TEMPLATE.md`) плюс реализация в `mcp/tools/` и проверка на фикстуре в
`tests/`. Карточке нужны те же `источник` и `check`, что правилу, и ещё
`идея` — откуда взят инструмент, с лицензией образца. Фикстуры — только свои
синтетические выгрузки с вымышленными именами: выгрузку типовой или клиентской
конфигурации в репозиторий не кладём.

## Пакет инструкций по конфигурации

Пакет — то, что набор знает про саму конфигурацию для помощника, работающего в
базе рядом с бухгалтером: `profile.json` (паспорт), `where_is.md`, `objects.md`,
`notes.md`, `faq.md`, `chips.json` в `tracks/<направление>/`; шпаргалки
платформы — `tracks/core/cheats/*.md`. Формат и ключи профиля — README,
«Пакет инструкций по конфигурации»; заготовка — `tracks/_PACK_TEMPLATE/`.

Что важно при пополнении. В промпт помощника уходит сжатая выжимка
(профиль, `where_is.md`, `notes.md`, чипы), поэтому пишем справочник, но
помним о потолке 24 КБ на выжимку — его считает манифест. Факт, которого ты не
подтвердил источником или живой базой, помечай `[проверить]` в той же строке:
в файле он останется (для ревью и `get_instructions_file`), в промпт не уйдёт.
Подробности — в разделы с заголовком `… (подробно)`, в `notes.md` держи раздел
«Коротко» с тезисами. Источники — номерами `S-n` в скобках по тексту и
списком с URL в `sources.md` (в файлах пакета URL не нужны); текст — своими
словами, как и у правил. У `ka` и `erp` общее лежит в `ut`, а у них — только
добавки и `"расширяет": "ut"` в профиле. Чистая комната та же, что у правил:
никаких имён клиентов, баз, людей и путей; никаких реквизитов конкретной базы —
это знания о типовой конфигурации, а не о чьей-то. Проверка:
`scripts/manifest.py --проверить`, `scripts/hygiene.py`, `scripts/tools-check.py`
(в нём тест чистоты и размера настоящего пакета `bp`).

Сетевой сервис (`mcp/httpd.py`) подхватывает слитый в `main` пакет сам в
течение нескольких минут; выкат ему не нужен. Ревизию с ошибкой манифеста он
не возьмёт — поэтому в `main` попадает только зелёное.

## Рецепты

Рецепт — «как сделать X по порядку», файл `tracks/<направление>/guides/how-NNN.md`
(заготовка — `scripts/new-guide.py`, шаблон — `tracks/_GUIDE_TEMPLATE.md`).
Берём только **добытый путь**: первая попытка не сработала или порядок шагов
неочевиден; он верен для любой базы; каждый шаг проверен. Получилось с первого
раза по документации — это не рецепт.

Обязательные поля: `id` (`how-001`, сквозная нумерация), `направление`,
`категория`, `платформы`, `заголовок`, `источник` (вид `практика:проект и дата,
где проверено`), `задача` (одна фраза: что получаем), `ключи`, `check`. Поле
`правила` — список id правил, на которые рецепт опирается: рецепт даёт порядок
шагов, а факты и запреты остаются в правилах и не пересказываются. Разделы:
«Шаги», «Проверка результата», «Где ломается». Серьёзности нет. Чистая комната та
же, что у правил. Через портал рецепт приходит конвертом
`Файл: tracks/<направление>/guides/how-XXX.md`; `scripts/hygiene.py --файл`
понимает оба вида.

## Перед коммитом

```bash
scripts/manifest.py     # пересобрать манифест
scripts/hygiene.py      # проверить гигиену
scripts/tools-check.py  # инструменты на фикстурах, сетевой режим, подгрузка знаний
```

Все три гоняются в CI на каждый push; там же собирается образ сетевого режима.
Правил сервера (`mcp/`) это тоже касается: stdio без флага отдаёт ровно девять
инструментов, с `--tools offline` — десять, и на это рассчитывают портал
(`tests/test_portal_contract.py`) и раннер. Новые инструменты — в своей группе.
