# Проверить поля запросов по выгрузке метаданных до прогона в базе

Зачем: «Поле не найдено» платформа показывает только при выполнении запроса, проверка
конфигурации и сборка молчат. Когда запросов десятки, а обращений к полям - сотни, первый
прогон в базе превращается в серию падений по одному. Сверка по файлам снимает их до
прогона. Это проверка имён, не замена прогону (см. «Где ломается»).

## Шаги

1. Взять выгрузку конфигурации той же версии, что и целевая база: из копии этой базы,
   `1cv8 DESIGNER /F <папка копии> /DumpConfigToFiles <каталог> /Out <журнал>`
   (иерархический формат). Выгрузка от другой версии показывает поля, которых в базе нет,
   и прячет те, что есть (mdo-012).
2. Собрать индекс полей по выгрузке: для каждого объекта (`Catalogs/<Имя>.xml`,
   `Documents/<Имя>.xml`, `InformationRegisters/<Имя>.xml`, `AccumulationRegisters/<Имя>.xml`
   и далее по видам) - имена `<Attribute>`, у регистров `<Dimension>` и `<Resource>`, у
   табличных частей `<TabularSection>` - их реквизиты отдельным ключом
   `<Вид>.<Имя>.<ТЧ>`. Стандартных реквизитов в XML нет, их добавить по виду объекта
   (например `Ссылка`, `Код`, `Наименование`, `ПометкаУдаления`, `Родитель`, `Владелец`,
   `ЭтоГруппа` у справочников; `Ссылка`, `Номер`, `Дата`, `Проведен` у документов; `Период`,
   `Регистратор`, `НомерСтроки`, `Активность` у регистров; `Ссылка`, `НомерСтроки` у
   табличных частей); какие из них есть у конкретного вида и при каких свойствах объекта -
   по синтакс-помощнику, не по памяти.
3. Вытащить тексты запросов из модулей (`.bsl`) и в каждом разобрать источники:
   `ИЗ <Вид>.<Имя> КАК <Псевдоним>` и каждое `СОЕДИНЕНИЕ ... КАК <Псевдоним>`; без `КАК`
   псевдоним равен имени таблицы. Затем собрать все обращения `<Псевдоним>.<Поле>` в
   выборке, условиях соединений, `ГДЕ`, `СГРУППИРОВАТЬ ПО`, `УПОРЯДОЧИТЬ ПО`.
4. Отделить то, что сверке по индексу не поддаётся, и пометить, а не считать ошибкой:
   временные таблицы и вложенные запросы (псевдоним указывает не на объект метаданных,
   их поля - по собственной выборке); виртуальные таблицы регистров (`.Остатки(...)`,
   `.Обороты(...)`, `.СрезПоследних(...)`: поля с суффиксами `Остаток`, `Приход`, `Расход`,
   `Оборот`); обращения через точку (`Поле.Подполе`) - сверять только первый сегмент.
5. Сверить оставшиеся пары с индексом: таблица есть, поле есть у неё или у её табличной
   части. Каждая находка - либо правка запроса, либо исключение из шага 4 с записью,
   почему. Повторять после каждой правки запросов.
6. Прогнать код в базе. Сверка ловит имена полей; типы, неоднозначные псевдонимы
   (query-003) и поля вариантов отчётов на СКД (query-006) она не видит.

## Проверка результата

- Ловушка на саму проверку: запрос с заведомо несуществующим полем сверка находит; если
  нет - разбор запросов или индекс пустой, результат «0 находок» ничего не значит.
- Счётчик разобранных обращений не нулевой и правдоподобный для объёма кода (в
  наблюдении - около 1900 на набор обработок).
- Прогон в базе после сверки не даёт «Поле не найдено» на сверенных запросах.

## Где ломается

- Выгрузка снята с другой версии конфигурации - сверка «проходит», а в базе поля нет
  (mdo-012).
- Ложные находки: виртуальные и временные таблицы, вложенные запросы, стандартные
  реквизиты, которых в XML нет, обращения через точку - шаг 4; без него список находок
  длиннее реальных ошибок.
- Текст запроса собран из кусков строк в коде - разбор по регулярному выражению видит
  только часть; такие запросы сверять по собранному тексту.
- Псевдоним таблицы совпадает с именем поля соседней таблицы - запрос падает по другой
  причине, имена при этом «правильные» (query-003).
- Поле есть в запросе и наборе, но его нет в варианте отчёта, или наоборот, - это
  уровень СКД, ловится прогоном вариантов (query-006).
- Та же идея для путей данных форм: `Объект.<Реквизит>` сверяется с объектом по тому же
  индексу (forms-002).
