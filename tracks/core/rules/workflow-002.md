# Отчёты 1С пишутся с BOM: якорь ^ в grep теряет первую строку, а json.load падает

## Симптом

Скрипт «не видит» первую строку файла-отчёта 1С, интерактивно grep её находит.

Второй вид того же: отчёт в JSON, который 1С записала, не разбирается питоном, хотя
глазами файл корректен:

```text
json.decoder.JSONDecodeError: Unexpected UTF-8 BOM (decode using utf-8-sig): line 1 column 1 (char 0)
```

## Причина

1С пишет текстовые файлы с BOM (EF BB BF). `grep '^МАРКЕР'` не совпадает на первой
строке: перед маркером стоит BOM. Интерактивный ugrep BOM пропускает, /usr/bin/grep
- нет.

## Правило

В скриптах, разбирающих файлы 1С, не использовать якорь `^` для маркеров
(`grep 'ОШИБКА;'` вместо `grep '^ОШИБКА;'`) либо срезать BOM явно.

Файлы 1С читать кодировкой `utf-8-sig`, а не `utf-8`: она снимает BOM, если он есть,
и работает, если его нет. Правило касается **любого** чтения, а не только JSON:
`json.load(open(path, encoding="utf-8-sig"))`, `io.open(path, encoding='utf-8-sig')`.
На `utf-8` разбор JSON падает сразу, а текстовые сравнения ломаются тихо - первый
символ первой строки оказывается `\ufeff`.

выполнялся, причём дефект был в тесте, а не в продукте.
