# -UpdateDBCfg в одной команде с /LoadConfigFromFiles конфигурацию базы не применяет

## Симптом

Сборочный скрипт грузит XML-выгрузку в базу и применяет её одной командой:

```
1cv8 DESIGNER /F <база> /LoadConfigFromFiles <каталог> -Format Hierarchical -UpdateDBCfg
```

Команда отрабатывает с `rc=0`, в журнале только безобидные предупреждения. А тесты продолжают
гонять код ПРОШЛОЙ сборки: новый сценарий в прогоне не появляется, номера строк в стеке ошибок
меньше фактических, новый реквизит в базе отсутствует.

Выгрузка конфигурации из базы при этом показывает НОВЫЙ код — потому что выгружается основная
конфигурация, а исполняется конфигурация базы данных.

## Причина

Ключ применяет основную конфигурацию, но конфигурация базы данных остаётся прежней. Признак —
отдельный запуск `/UpdateDBCfg` сразу после «успешной» загрузки каждый раз печатает «Обработка
структуры базы данных…»: работа для него оставалась.

## Правило

Применение — отдельной командой после загрузки, а не ключом внутри неё:

```
1cv8 DESIGNER /F <база> /LoadConfigFromFiles <каталог> -Format Hierarchical
1cv8 DESIGNER /F <база> /UpdateDBCfg
```

Шаг идемпотентный: применять нечего — команда просто отвечает успехом. Его код возврата проверяется
отдельно от кода возврата загрузки.

## Как проверить

Прогон, который исполняет код из базы (тесты уровня 3, смок форм), сверяется с тем, что в
исходниках: новый сценарий обязан появиться в списке, новый реквизит — читаться.

Выгрузка конфигурации из базы для этой проверки НЕ годится: она отдаёт основную конфигурацию, а та
обновилась.

## История

maERP, 2026-09-20. Новый сценарий уровня 3 не появлялся в прогоне после двух полных
пересборок базы подряд. Сначала подозревали кэш экспорта EDT, потом кэш клиента: выгрузка
конфигурации ИЗ БАЗЫ показывала новый код, и это увело в сторону на час. Разницу «основная
конфигурация против конфигурации базы данных» показал отдельный `/UpdateDBCfg`, который отработал
не вхолостую — после него сценариев стало на один больше.
