# Псевдоним таблицы, совпадающий с именем поля соседней таблицы, делает поле неоднозначным

## Симптом

Ошибка выполнения запроса «Неоднозначное поле "Представления.Ссылка"» (в локали клиента —
«Campo ambiguo»), хотя каждое поле в тексте квалифицировано псевдонимом. В EDT и при
CheckConfig запрос проходит: ошибка только на выполнении.

## Причина

Псевдоним одной таблицы соединения совпадает с именем поля другой. Тогда
`Псевдоним.Ссылка` платформа читает двояко: поле таблицы с таким псевдонимом или
поле-ссылка внутри одноимённого поля соседней таблицы. Пойманные случаи:

- `Реквизиты` (ПВХ) + её табличная часть под псевдонимом `Представления`: у главной
  таблицы есть поле-табличная часть `Представления`, и `Представления.Ссылка` — либо
  присоединённая таблица, либо `Реквизиты.Представления.Ссылка`;
- `Справочник.Номенклатура КАК Номенклатура` + табличная часть техкарты, у которой есть
  поле `Номенклатура` (сырьё): `Номенклатура.Ссылка` — либо главная таблица, либо
  `ТехнологическаяКарта.Номенклатура.Ссылка`;
- **измерение регистра** с именем присоединённого справочника:
  `РегистрСведений.ИзбраннаяНоменклатураРМК КАК Избранное` с измерением `Номенклатура`
  плюс `ВНУТРЕННЕЕ СОЕДИНЕНИЕ Справочник.Номенклатура КАК Номенклатура` —
  `Номенклатура.ПометкаУдаления` читается и как поле справочника, и как
  `Избранное.Номенклатура.ПометкаУдаления`. То есть опасны не только табличные части:
  любое поле-ссылка любой таблицы области видимости годится.

Обращение падает **всегда**, а не на некоторых данных: имя не разрешается на этапе
разбора запроса. Значит функция, единственный запрос которой так написан, не работала
ни разу — в maERP плитки избранного РМК были нерабочими 14 сборок, с самого появления.

```bsl
// НЕПРАВИЛЬНО: псевдоним = имя табличной части главной таблицы
"... ИЗ ПланВидовХарактеристик.ДопРеквизиты КАК Реквизиты
|	ЛЕВОЕ СОЕДИНЕНИЕ ПланВидовХарактеристик.ДопРеквизиты.Представления КАК Представления
|	ПО Представления.Ссылка = Реквизиты.Ссылка"

// ПРАВИЛЬНО: псевдоним не совпадает ни с одним полем соединяемых таблиц
"...	ЛЕВОЕ СОЕДИНЕНИЕ ПланВидовХарактеристик.ДопРеквизиты.Представления КАК Заголовки
|	ПО Заголовки.Ссылка = Реквизиты.Ссылка"

// НЕПРАВИЛЬНО: у ТехнологическаяКарта есть поле Номенклатура
"ИЗ Справочник.Номенклатура КАК Номенклатура
|	ЛЕВОЕ СОЕДИНЕНИЕ Справочник.Номенклатура.ТехнологическаяКарта КАК ТехнологическаяКарта
|	ПО Номенклатура.Ссылка = ТехнологическаяКарта.Ссылка"

// ПРАВИЛЬНО
"ИЗ Справочник.Номенклатура КАК Продукция ... ПО Продукция.Ссылка = ТехнологическаяКарта.Ссылка"
```

## Как проверить

Псевдонимы всех таблиц соединения сверить с именами полей остальных таблиц запроса
(реквизиты, табличные части, измерения, ресурсы). Особенно опасны псевдонимы по имени
объекта (`КАК Номенклатура`, `КАК Контрагент`): такие поля есть почти у любой табличной
части и у половины регистров. Прогоном ловится смоком форм, если запрос выполняется при
открытии, и тестами проведения уровня 3, если он в проведении.

**Грепом это не ищется.** В maERP 2026-09-26 «псевдоним равен имени поля соседней
таблицы» дал 249 совпадений, из которых настоящим был один: остальные — псевдонимы
колонок списка выборки (`СУММА(...) КАК Количество`), которые через точку не
разыменовываются и держателями полей не являются. Рабочий метод — разбор запроса:
области видимости отдельно для каждой части пакета (по «;»), для каждого подзапроса и
для каждой ветки `ОБЪЕДИНИТЬ`; псевдонимы берутся только у источников (`ИЗ`,
`СОЕДИНЕНИЕ`), состав полей — из `.mdo`, а для временных таблиц выводится из списка
выборки их `ПОМЕСТИТЬ`-части. Признак дефекта: обращение `P.<поле>`, которое
разрешается и через псевдоним `P`, и через неявную навигацию по одноимённому полю.

## История

maERP 2026-09-08: запрос `УправлениеСвойствами.СвойстваОбъекта` заголовков дополнительных
реквизитов по языку; карточка номенклатуры не открывалась. Псевдоним переименован в 2.0.14.22.
Тем же днём тесты уровня 3 поймали второй случай в `ТоварыВНаличии.КоэффициентыТехкарт`:
проведение выпуска продукции и поступления из переработки падало. После переименования
первого псевдонима упал второй: `КАК ТехнологическаяКарта` против табличной части
`Номенклатура.ТехнологическаяКарта`. Переименовывать все псевдонимы запроса сразу
(2.0.14.25–26).

2026-09-26, maERP. Третий случай, найденный смоком при подготовке релиза: форма
избранного рабочего места кассира не открывалась, `Поле не однозначно
"Номенклатура.ПометкаУдаления"`. Здесь совпало имя присоединённого справочника с
**измерением регистра**, а не с табличной частью, — правило пришлось расширить: держателем
одноимённого поля может быть любая таблица области видимости.

Тем же днём вся конфигурация разобрана анализатором: 579 текстов запросов в модулях, 63
запроса динамических списков форм, 62 набора данных отчётов, 1536 областей видимости,
2559 источников. Других мест нет. Метод контролировался на git-истории и воспроизводит
все четыре исторических дефекта проекта — это и есть проверка, что такой анализ ловит
класс, а не только уже известные строки.
