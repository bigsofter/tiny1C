# Поле в настройках варианта отчёта, которого нет в запросе набора: «Поле не найдено» при формировании

## Симптом

Отчёт открывается, при нажатии «Сформировать» — ошибка, результата нет:

```
Поле не найдено "Подразделение"
Campo no encontrado "Подразделение"
```

Проверка конфигурации молчит, XML схемы корректен, смок «открыть все формы»
проходит: форма отчёта открывается, падает только формирование. Отчёт может годами
стоять в меню нерабочим — его просто никто не формирует.

## Причина

У поля в схеме компоновки три уровня, и платформа сверяет их только при
формировании:

1. запрос набора данных выбирает поле (`... КАК МестоХранения`);
2. набор объявляет его (`<field><dataPath>МестоХранения</dataPath>`);
3. вариант настроек на него ссылается (`<dcsset:field>` в группировке, выборе,
   отборе, порядке).

Ошибка «Поле не найдено» — разрыв между уровнями. Он появляется, когда меняют
одно, а остальное оставляют:

- переименовали или удалили измерение регистра, поправили запрос — а группировка
  варианта осталась на старом имени;
- скопировали вариант с соседнего отчёта (поставщики ← покупатели) вместе с полями
  чужого набора;
- поле объявлено в наборе (уровень 2), но запрос его не выбирает (уровень 1) —
  пока на поле никто не ссылается, это безвредно; первая же группировка по нему
  даёт ту же ошибку.

Неиспользуемое объявленное поле платформа молча отбрасывает, поэтому уровень 2 без
уровня 1 сам по себе не ошибка — ошибкой его делает ссылка из варианта.

```xml
<!-- неправильно: группировка по полю, которого нет ни в запросе, ни в регистре -->
<dcsset:item xsi:type="dcsset:GroupItemField">
  <dcsset:field>Подразделение</dcsset:field>
</dcsset:item>

<!-- правильно: поле выбрано запросом и объявлено в наборе -->
<!-- запрос:  УбыткиОбороты.МестоХранения КАК МестоХранения, -->
<field xsi:type="DataSetFieldField">
  <dataPath>МестоХранения</dataPath>
  <field>МестоХранения</field>
</field>
<!-- вариант: -->
<dcsset:field>МестоХранения</dcsset:field>
```

## Правило

Поле, на которое ссылается вариант настроек, должно быть выбрано запросом набора и
объявлено в наборе. При переименовании или удалении измерения регистра, реквизита
документа или поля запроса — искать имя по всем `Template.dcs` и править варианты
вместе с запросом. Чинить вариант заменой поля на ближайший смысловой аналог
(подразделение → место хранения), а не удалением уровня группировки: структура
отчёта, к которой привыкли пользователи, сохраняется.

Чистить сохранённые пользователями настройки не нужно: их платформа сопоставляет с
новой схемой и неизвестные поля отбрасывает.

## Как проверить

Статически по файлам разрыв надёжно не находится: поля вложенных наборов,
объединений, вычисляемые поля, ресурсы, параметры и поля через точку дают десятки
ложных находок (прототип на 56 вариантах maERP — 33 отчёта «с замечаниями», из
них реально падают 4).

Ловит прогон: каждый вариант каждого отчёта со схемой — `Отчет.КомпоновщикНастроек
.ЗагрузитьНастройки(Вариант.Настройки)`, заполнить пустые параметры (период — этот
год, ссылочные — первый элемент справочника, иначе отчёт падает на параметре, а не
на поле), `СкомпоноватьРезультат`. Без внешнего соединения — внешней обработкой
через тонкий клиент `/Execute`. Чтобы проверить правку до загрузки в базу, схему
читают из файла: `СериализаторXDTO.ПрочитатьXML(Чтение, Тип("СхемаКомпоновкиДанных"))`
и компонуют её `КомпоновщикМакетаКомпоновкиДанных` с настройками варианта.

## История

maERP, 2026-10-02. При перестройке меню отчётов прогнали все 56 вариантов
отчётов конфигурации. Четыре упали:

- «Затраты» (стоял в меню Казначейства): группировка по «Подразделение» — такого
  измерения у регистра нет; при этом поля «МестоХранения» и
  «ХозяйственнаяОперация» были объявлены в наборе, но запрос их не выбирал;
- «Просроченные долги поставщиков»: вариант скопирован с покупательского, ссылается
  на «РеализацияТоваровУслуг»;
- «Движения товара», вариант «Отчёт по списанию»: поле «Склад» от старого
  регистра;
- «Отчёт по проводкам»: «Количество Дт» в группировке «Заголовок» — смежная ошибка
  структуры варианта, ловится тем же прогоном.

Первая правка «Затрат» — только замена поля в группировке — проверкой схемы из
файла дала ту же ошибку уже на «МестоХранения»: поле было объявлено, но не
выбрано запросом. Отсюда правило про три уровня.
